# 테스트 커버리지

> 최종 업데이트: 2026-08-04
> 상위 문서: [`CLAUDE.md`](../../CLAUDE.md) · 관련: [`CI`](../../문서/CI.md) · [`server-tdd`](../.claude/skills/server-tdd/SKILL.md)

서버 테스트가 코드의 어디를 지나갔는지 재는 방법과, **그 숫자를 어디까지 믿을 수 있는지**를 정리한다.

---

## 1. 실행

```powershell
powershell -File Server/run-coverage.ps1          # 낮은 순 25개 + 전체 수치
powershell -File Server/run-coverage.ps1 -Top 0   # 전부
powershell -File Server/run-coverage.ps1 -Html    # HTML 리포트까지 만들고 연다
```

HTML은 `reportgenerator` 전역 도구가 필요하다(1회 설치).

```powershell
dotnet tool install -g dotnet-reportgenerator-globaltool
```

> `-Html`은 테스트를 다시 돌린다. 이미 모아 둔 XML로 리포트만 다시 만들려면 직접 부른다.
>
> ```powershell
> reportgenerator -reports:"Server/WSGameServer.Tests/TestResults/*/coverage.cobertura.xml" `
>                 -targetdir:"Server/WSGameServer.Tests/TestResults/report" -reporttypes:Html
> ```

결과는 `Server/WSGameServer.Tests/TestResults/` 아래에 쌓이며 **`.gitignore` 처리돼 있다.**
실행할 때마다 새 GUID 폴더가 생기므로 스크립트가 먼저 비우고 시작한다.

## 2. ⚠️ 필터 없이 재면 숫자가 쓸모없다

`--collect:"XPlat Code Coverage"`만 쓰면 **MemoryPack이 만든 `*.g.cs`가 전체 라인의 절반을 넘게**
차지한다. 사람이 쓰지 않은 코드가 분모를 부풀려, 정작 손으로 쓴 코드가 얼마나 덮였는지가 묻힌다.

| | 대상 파일 | 전체 커버리지 |
| --- | --- | --- |
| 필터 없음 | 79개 | **17.5%** |
| 필터 적용 | 38개 | **45.4%** |

제외 규칙은 [`Server/coverlet.runsettings`](../coverlet.runsettings)에 있다.

| 제외 대상 | 이유 |
| --- | --- |
| `**/*.g.cs` | MemoryPack 포매터·소스 제너레이터 산출물 |
| `[MikaNetwork.*]*` | **게임을 모르는 재사용 프레임워크.** 관심사가 달라 섞이면 "게임 로직이 얼마나 덮였나"가 흐려진다 |
| `[MikaUtils]*` | 같은 Lib 소속인데 **어셈블리 이름에 `MikaNetwork`가 없어** 위 패턴에 안 걸린다 |
| `[MikaProtocol]*` | 패킷 DTO. 프로퍼티 선언뿐이라 덮을 로직이 없다 |
| `[GameData]*` | 엑셀에서 생성된 테이블 정의 |

> 남은 어셈블리가 `WSGameServer` 하나뿐이라, 출력 경로가 그 아래 상대경로로 나온다
> (`User/Currency/CurrencyWallet.cs`). 제외 목록을 바꾸면 이 표기도 함께 바뀐다.

> **MemoryPack 포매터에는 `[GeneratedCode]` 속성이 붙지 않는다.** `// <auto-generated/>` 주석만
> 있어서 `ExcludeByAttribute`로는 안 걸린다 — **파일 패턴으로** 걸어야 한다.

> `MikaNetwork.*`를 뺐다고 검증을 포기한 게 아니다. 게임 규칙에 걸린 부분
> (유휴 세션 판정 등)은 `WSGameServer` 쪽 테스트가 이미 잡는다.

## 3. "덮였다"의 기준

**그 줄이 테스트 도중 한 번이라도 실행됐는가**, 그것뿐이다.

```xml
<line number="8" hits="8" branch="False" />
```

`hits > 0`이면 초록, `0`이면 빨강.

### ⚠️ 실행 ≠ 검증

**단언이 하나도 없어도 그 줄을 지나가기만 하면 초록이 된다.**

```csharp
[Fact]
public void 이것도_커버리지를_올린다()
{
    user.AssignWorkStation(0, ItemType.Fishing, 500, Base);
    // 단언 없음 — 그래도 AssignWorkStation의 모든 줄이 초록이 된다
}
```

실제로 `ServerLog`가 60%대인데, **로그를 검증한 테스트는 하나도 없다.**
다른 테스트가 도는 동안 로그가 찍혀서 초록이 됐을 뿐이다.

> **빨강만 믿을 만하고 초록은 못 믿는다.**
> 커버리지는 *"여기는 확실히 안 봤다"* 를 알려주는 도구지,
> *"여기는 안전하다"* 를 보증하지 않는다. **커버리지를 목표로 삼으면 안 되는 이유**가 이것이다 —
> 단언 없는 테스트로도 숫자는 얼마든지 올라간다.

### 줄 커버리지와 분기 커버리지

```
line-rate   0.4555   ← 스크립트가 출력하는 값
branch-rate 0.5206   ← 함께 수집되지만 출력하지 않는 값
```

`if` 안에 들어간 적이 있으면 줄은 초록이지만, **`else`를 한 번도 안 타도 초록**일 수 있다.
분기 커버리지는 그것을 따로 센다. HTML 리포트에는 둘 다 나온다.

## 4. 임계값을 걸지 않는다 (지금은)

**커버리지 때문에 빌드가 실패하지 않는다.** `dotnet test`의 성패는 테스트가 통과했는가뿐이고,
커버리지는 옆에서 세는 숫자다. CI도 마찬가지로 **보여주기만** 한다.

이유는 두 가지다.

1. **걸 만한 숫자가 아직 없다.** `CurrencyWallet` 3.3%, `GachaService` 0% —
   어떤 선을 그어도 즉시 빨개진다.
2. **3장의 함정 때문이다.** 임계값은 "숫자를 올려라"라는 압력이 되는데, 그 압력은
   단언 없는 테스트로도 해소된다. 숫자가 자리 잡은 뒤에 거는 것이 순서다.

> 나중에 걸려면 `coverlet.collector`(현재)로는 안 되고 **`coverlet.msbuild`** 로 바꿔
> `/p:Threshold=60` 형태를 써야 한다. collector 방식은 임계값 실패를 지원하지 않는다.

## 5. 현재 구멍 (2026-08-04 · 전체 45.4% · 줄 938/2064)

우선순위 순이다. 위쪽이 **결함이 숨을 자리가 많고 열기도 쉽다.**

| 파일 | 커버리지 | 메모 |
| --- | --- | --- |
| `User/Currency/CurrencyWallet.cs` | **3.3%** (2/60) | **재화가 오가는 유일한 지점.** 순수 코어라 의존이 없는데도 비어 있다 |
| `User/User.Currency.cs` | **0%** (0/66) | 위와 한 쌍 |
| `Gacha/GachaService.cs` | **0%** (0/68) | 추첨기(`GachaPoolCatalog`)는 61.5% 덮였는데 서비스는 0 |
| `User/User.DB.cs` | **0%** (0/78) | 로그인 적재 흐름. `Entity.Create`가 비동기라 막혀 있다 |
| `Network/ClientPacketHandler.cs` | **0%** (0/80) | `EResultCode` 규약 분기 |
| `Repository/*.cs` | 0~57% | SQL. `:memory:` 커넥션으로 열 수 있다 |

### 잘 덮인 곳 (기준선)

`WorkSpeed` 100% · `WeightedPicker` 98.6% · `WorkStationSlot` 98.3% · `Character` 95% ·
`WorkStation` 94.1% · `DropTable` 79.3% · `User.WorkStation` 74.4%

**전부 순수 코어이거나, seam을 열어 준 곳이다.** `User.WorkStation`이 74.4%인 것은
2026-08-03 리팩터링(채널·DB 큐 주입)의 직접적인 결과다.

### 덮지 않아도 되는 곳

`Program.cs` · `NetworkManager` · `SessionWatchdog` · `DBManager` · `PacketLogger` ·
`SessionUserExtensions` 는 **배선과 타이머**다. 판정 본체는 따로 빠져 있고 그쪽이 이미 덮여 있다
(예: `SessionWatchdog`는 0%지만 그 본체인 `MikaServer.DisconnectIdle`은 테스트 6건이 잡는다).

> **배선을 덮으려고 테스트를 쓰지 않는다.** 숫자는 오르지만 잡는 결함이 없다.

## 6. CI

`.github/workflows/server-ci.yml`이 push·PR마다 빌드 → 테스트 → 커버리지를 돌리고
**실행 화면(Job Summary)에 커버리지 표를 남긴다.**

- 테스트가 실패하면 CI가 실패한다.
- **커버리지 수치로는 실패시키지 않는다** (4장).
- Unity 미러 동기화(`sync-protocol-to-unity.ps1`·분석기 복사)는 CI에서 건너뛴다 —
  러너에는 Unity 프로젝트를 갱신할 이유가 없다.
