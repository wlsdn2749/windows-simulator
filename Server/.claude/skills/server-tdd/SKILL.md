# 서버 TDD — WSGameServer.Tests

테스트 먼저(red) → 통과시키는 최소 구현(green)의 루프를 돌리되,
**리팩토링해도 살아남는 테스트**만 남긴다. 절차와 판단 기준을 모두 담는다.

```powershell
dotnet test Server/WSGameServer.Tests/WSGameServer.Tests.csproj
```

| 항목 | 규칙 |

## 루프의 규칙

1. **red 먼저.** 실패하는 테스트를 쓰고 실패를 확인한 뒤, 통과시키는 **최소한**만 구현한다.
   미래 테스트를 내다본 선구현·추측성 기능을 넣지 않는다.
2. **한 번에 한 조각.** 테스트 하나 → 구현 하나 → 반복. 테스트를 몰아서 먼저 다 쓰는 것
   (수평 분할)은 금지 — 상상 속 동작을 검증하게 되고, 구현이 가르쳐 주는 것을 반영할 수 없다.
3. **리팩토링은 루프 밖.** red-green 사이클 안에서 구조를 고치지 않는다. 녹색을 만든 뒤 별도로 한다.

## 어디에서 테스트하는가 — 이음새 합의

테스트는 **공개 인터페이스에서만** 건다. 내부에 손을 넣어야 검증이 된다면
테스트가 아니라 **모듈의 모양이 잘못된 것**이다.

- 테스트를 쓰기 전에 **어느 인터페이스를 검증할지 먼저 정하고 사용자와 합의한다.**
  모든 것을 테스트할 수는 없다 — 합의가 곧 "노력을 어디에 쓸지"의 결정이다.
- 이 서버에서 좋은 이음새의 예: `WorkSpeed.From(...).Add(...).Resolve()`,
  `WorkStationSlot`의 정산 경로, `WeightedPicker`·`DropTable`의 추첨 결과.
- private 메서드·리플렉션·내부 필드 검증은 금지. 필요해 보이면 모듈을 나누는 신호다.

## 좋은 테스트의 기준

**동작(WHAT)을 검증하고, 구현(HOW)에 결합하지 않는다.** 구현을 통째로 바꿔도
동작이 같으면 테스트는 통과해야 한다. 깨지면 그 테스트는 리팩토링 방해물이다.

### 기대값은 독립적으로 계산한 리터럴로 적는다

기대값을 **코드와 같은 방식으로 재계산하면** 그 테스트는 항상 통과한다(동어반복).
손으로 계산한 값을 리터럴로 적고, **계산 근거를 주석으로** 남긴다.

```csharp
// ✅ 이 저장소의 실제 예 (WorkSpeedTest) — 근거를 주석으로, 값은 리터럴로
[Fact]
public void 가산끼리는_합한_뒤_한_번만_적용된다()
{
    // 특성 +25% + 부스트 +100% = +125% → 1800 × 2.25 = 4050
    // 서로 곱하면 1800 × 1.25 × 2.0 = 4500이 된다. 그 차이가 이 테스트의 전부다.
    WorkSpeed.From(1800).Add(250).Add(1000).Resolve().ShouldBe(4050);
}

// ❌ 동어반복 — 구현과 같은 식으로 기대값을 만들면 절대 실패하지 않는다
var expected = (long)baseSpeed * (Scale + add) / Scale;
WorkSpeed.From(baseSpeed).Add(add).Resolve().ShouldBe((int)expected);
```

- 나누어떨어지지 않는 값을 일부러 고른다 — 절단·반올림 실수가 드러난다
  (`Aptitude4 = 1800`이 그 예다).
- 논리적 단언은 테스트당 하나. 여러 성질은 테스트를 나눈다.

### 구현 결합의 신호 (전부 금지)

- 자기 모듈·내부 협력자를 목으로 만든다
- 호출 횟수·호출 순서를 단언한다
- 인터페이스를 우회해 검증한다 (결과를 인터페이스로 되읽지 않고 DB를 직접 쿼리)
- 테스트 이름이 WHAT이 아니라 HOW를 서술한다 (`~를_호출한다`)

## 목(Moq)은 시스템 경계에서만

| 목으로 대체한다 | 목으로 만들지 않는다 |
| --- | --- |
| 시각 (`DateTime.UtcNow` 류) | 자기가 만든 도메인 모듈 (`WorkSpeed`·`Inventory` …) |
| 난수 (드롭 롤의 `Random`) | 내부 협력자 |
| DB (SQLite 연결) | 우리가 통제하는 모든 것 |

- **경계 의존성은 생성하지 말고 주입받게 설계한다.** 메서드 안에서 `new`·static으로
  시각·난수를 얻으면 그 모듈은 테스트할 수 없다 — 파라미터나 생성자로 받는다.
- 지금 테스트들이 Moq 없이 도는 이유는 대상(`WorkSpeed` 등)이 **순수 계산**이기 때문이다.
  정상이다. 목이 필요 없는 모양이 가장 좋은 모양이다 — Moq는 경계가 낄 때만 꺼낸다.

## 버그 수정 절차

버그는 **재현하는 실패 테스트부터** 쓴다. 수정 후 그 테스트가 회귀 방지선으로 남는다.
"고치고 나서 테스트 추가"는 순서가 반대다 — 테스트가 정말 그 버그를 잡는지 확인할 기회가 사라진다.
