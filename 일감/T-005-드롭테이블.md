# T-005 산업 4종 드롭 테이블 · 아이템 TID 대역 · 확률 테이블 연결

> **2026-07-31 범위 확대 · 보류 해제.**
> 기존 범위는 "드롭 시트 4개 추가"였는데, **아이템 TID 대역 규칙**과
> **희귀도 확률 테이블 연결**이 함께 가야 한 번에 끝난다. 따로 하면 두 번 고친다.

## 배경

산업 5종 중 **낚시만** 드롭 테이블이 있다(`FishingBasicTable`).
나머지 4종은 슬롯에 배치해도 정산 때 테이블이 없어 조용히 건너뛴다:

```
WRN [채취] 드롭 테이블 없음, 건너뜀: Mining (슬롯 0)
```

즉 **배치는 되는데 아무것도 안 나온다.** 예외로 죽지는 않게 막아 뒀지만
산업 4종이 사실상 비어 있다.

### 구조 — 산업별 단일 테이블 (2026-07-31 확정)

**`RarityWeightTable`(전 산업 공통 분포)을 두지 않는다.**
가중치는 각 산업의 드롭 시트가 직접 갖는다 — 낚시 기존 구조를 5종이 그대로 공유한다.

```
<산업>BasicTable :  DropTID(키) | ItemTID(Ref) | Weight | Description
```

| | 내용 |
| --- | --- |
| ✅ 얻음 | **산업별 분포 차별화** — 낚시를 상위로 기울이거나 채굴을 깊이로 올릴 수 있다 |
| ✅ 얻음 | 롤이 판정당 2회 → **1회** |
| ⚠️ 잃음 | 단일 원본. **확률 조정 시 5개 시트를 함께** 봐야 한다 |

> 기획 문서가 잡고 있던 "분포는 전 산업 동일 · `RarityWeightTable` 단일 원본"은
> **2026-07-31에 폐지됐다.** → [자원채취](../GameDesign/기획/자원채취/README.md) 2.4

## 아이템 TID 대역

산업마다 **10000 단위**로 대역을 나누고, 대역 안에서 **희귀도 순으로 `+1 ~ +6`** 을 쓴다.

| 산업 | 대역 | 상태 |
| --- | --- | --- |
| **낚시** | `10001 ~ 10006` | ✅ 확정 (2026-07-31) |
| **농사** | `20001 ~ 20006` | ✅ 확정 |
| **벌목** | `30001 ~ 30006` | ✅ 확정 |
| **채굴** | `40001 ~ 40006` | ✅ 확정 |
| **사냥** | `50001 ~ 50006` | ✅ 확정 |

대역 안의 끝자리는 희귀도 고정이다 — `+1` Common · `+2` Uncommon · `+3` Rare ·
`+4` Epic · `+5` Legendary · `+6` Mythic.
아이템 문서 1.4가 요구한 **최소 30종**(5산업 × 6등급)이 이걸로 채워진다.

**대역은 산업당 10000개다.** 6종을 다 쓰고도 9994개가 남으므로,
같은 산업에 아이템이 늘어도(채굴 깊이 구간 · 사냥터별 산출물 · 낚시터 확장)
**대역 안에서 뒤로 이어 붙이면 된다.** 다음 대역을 침범하지 않는다.

> ⚠️ **대역 순서가 `ItemType` enum 순서와 다르다** (enum은 `Farming=1, Fishing=2, …`).
> `ItemTID / 10000` 으로 산업을 역산할 수 없다는 뜻이므로, **역산에 의존하는 코드를 쓰지 않는다.**
> 산업은 언제나 `ItemTable.ItemType`에서 읽는다.

### ⚠️ 낚시는 이설이다 — 신규 채번이 아니다

낚시 아이템은 **이미 `1001~1006`을 쓰고 있다** (`DataLog/ItemTable.json`).
10000대로 옮기는 것은 **살아 있는 TID를 옮기는 것**이라 게임기획코어 4장 식별자 규칙에 걸린다.

**`1001~1006`은 영구 결번으로 확정됐다 (2026-07-31).** 다른 아이템에 다시 붙이지 않는다.

남은 것은 이미 지급된 행의 처리뿐이다:

| 확인 | 내용 |
| --- | --- |
| 선행 확인 | **`t_user_inventory`** 에 `item_tid` = `1001~1006` 행이 있는가 |
| 있고 버려도 되면 | 개발 DB를 비우고 이설 (가장 단순) |
| 있고 못 버리면 | `UPDATE t_user_inventory SET item_tid = item_tid + 9000 WHERE item_tid BETWEEN 1001 AND 1006` |
| 없으면 | 그냥 엑셀만 고치면 된다 |

> 이 행을 방치하면 **인벤토리에 `ItemTable`에 없는 TID가 남는다.** 조회 시점에 이름·희귀도를
> 못 찾아 터지거나 빈칸으로 표시된다. 엑셀 이설과 **같은 작업 단위**에서 처리한다.

## 아이템 30종 — 산업 문서의 산출물 이름을 그대로 쓴다

임시 이름(`일반 생선` · `A`~`F`)을 버리고 **각 산업 기획안의 산출물 실명**으로 채운다.

낚시 문서 4장의 패턴을 5산업에 공통 적용한다 — **같은 자원의 상위 등급은 별도 `ItemTID`** 이며,
등급이 올라갈수록 이름이 구체적·희소해진다 (`붕어` → `월척 붕어` → `대물 잉어`).

| 희귀도 | 낚시 `1000_` | 농사 `2000_` | 벌목 `3000_` | 채굴 `4000_` | 사냥 `5000_` |
| --- | --- | --- | --- | --- | --- |
| `Common` | **붕어** 📖 | 밀 | 잡목 | **돌덩어리** 📖 | 질긴 고기 |
| `Uncommon` | **잉어** 📖 | 감자 | 소나무 목재 | 구리 광석 | 토끼 가죽 |
| `Rare` | **월척 붕어** 📖 | 옥수수 | 참나무 목재 | **은광석** 📖 | 늑대 가죽 |
| `Epic` | **향어** 📖 | 인삼 | 흑단 목재 | 금광석 | 곰 모피 |
| `Legendary` | **대물 잉어** 📖 | 변종 인삼 | **고급 원목** 📖 | 보석 원석 | 거대한 뿔 |
| `Mythic` | **전설의 잉어** 📖 | 태초의 씨앗 | 세계수 가지 | 심연의 원석 | 마수의 심장 |

📖 = 기획 문서에 이미 적혀 있는 이름 (낚시 4장 · 채굴 1장 · 벌목 3장). **나머지는 제안**이며,
`MaxStack`은 낚시 기준(`9999`)을 따른다 — 방치로 대량 축적되므로 크게 잡는다 (아이템 2장).

> 각 산업 문서의 산출물 서술과 대응한다 —
> 농사 "작물류(곡물·채소) · **변종 작물**", 벌목 "목재(수종별 등급) · **고급 원목**",
> 채굴 "광석(깊이별 등급) · **보석류**", 사냥 "**가죽 · 고기** · 뿔 · 모피".

### 이 표에서 의도적으로 뺀 것

| 항목 | 이유 |
| --- | --- |
| 낚시 `낡은 장화` | 실패(허탕)를 폐기했는데 "꽝 느낌" 아이템을 `Common`에 넣으면 실패를 다른 형태로 되살린다. **낚시의 "확실한 도파민" 정의와 어긋난다** (낚시 7장 Q5) |
| 채굴 깊이별 매핑 | 깊이 시스템이 미구현이다. **지금은 깊이 1구간(6종)만** 만들고, 구간이 늘면 `40007~`로 이어 붙인다 |
| 사냥터별 산출물 | 사냥터가 미확정이다. 지금은 사냥터 1개 기준 6종. 늘면 `50007~` |

### DropTID는 없앤다

현재 `FishingBasicTable.DropTID`가 **`10001~10006`** 이라, 아이템 TID를 10000대로 옮기면
**두 숫자가 완전히 겹친다.** 테이블이 달라 기술적 충돌은 없지만 로그·쿼리에서 구분이 안 된다.

구조를 기획대로 바꾸면 `Rarity`가 키가 되므로 **`DropTID` 컬럼 자체가 사라진다.** 그걸로 해결한다.
