# 서버 아키텍처 리뷰 — 2026-08-01

> 대상: `Server/` 전체 (WSGameServer + MikaNetwork.Lib + Repository, ~8.6k LOC)
> 방법: 전수 정독 후 "깊어지기(deepening) 기회" — 얕은 모듈, seam 누수, 테스트 불가 지점 — 를 후보로 정리.
> 시각 리포트: [서버아키텍처리뷰.html](서버아키텍처리뷰.html) (브라우저로 열기)

## 용어

| 용어 | 의미 |
| --- | --- |
| 모듈 | 인터페이스와 구현을 가진 모든 것 (함수·클래스·패키지) |
| 인터페이스 | 호출자가 알아야 하는 전부 — 시그니처 + 불변식 + 순서 제약 + 오류 모드 |
| 깊은/얕은 | 작은 인터페이스 뒤에 많은 동작 = 깊다. 인터페이스가 구현만큼 복잡 = 얕다 |
| seam | 그 자리를 고치지 않고 동작을 바꿀 수 있는 지점. 인터페이스가 사는 곳 |
| 어댑터 | seam에서 인터페이스를 충족하는 구체물. **어댑터 1개 = 가설상의 seam, 2개 = 진짜 seam** |
| 레버리지 | 호출자가 얻는 것 — 배운 인터페이스 단위당 쓸 수 있는 동작량 |
| 지역성(locality) | 유지보수자가 얻는 것 — 변경·버그·검증이 한 곳에 모임 |

## 현재 위치 요약

**순수 코어는 이미 깊다.** `WorkStationSlot`(214줄) · `WorkSpeed` · `WeightedPicker` · `DropTable` · `TableSet`은
값 + 주입된 협력자(`now` 인자, `Random?` 주입) 형태라 테스트 46건이 전부 여기 있다.

**문제는 정확히 한 단계 위다.** `User`(6개 partial, 441줄) · 리포지토리 · `GatheringScheduler`가
`ISession` / `DateTime.UtcNow` / `*.Instance` 싱글턴에 직결되어 있고,
**테스트 0%인 코드의 경계선이 이 세 가지가 처음 등장하는 지점과 정확히 일치한다.**
재화가 실제로 생성되는 모든 경로(정산 → 지급 → 저장 → 푸시)가 테스트 불가다.

| | 커버됨 (46건) | 커버 0건 |
| --- | --- | --- |
| 대상 | `WorkStationSlot` `WorkStation` `WorkSpeed` `WeightedPicker` `DropTable` `Character`(일부) | `User` 전체 · 리포지토리 5종 · `GachaService`/`GachaTable` · `UserManager` · `GatheringScheduler` · 패킷 핸들러 · `Inventory` · `CurrencyWallet` |
| 왜 | `now`·난수 주입, 의존성 없음 | `ISession` 필수 생성자(`User.cs:31`, internal), `DateTime.UtcNow` 직접 호출 7곳, 싱글턴 15곳, 실제 DB 필요 |

> `Inventory`와 `CurrencyWallet`은 의존성이 없어 **지금도 테스트 가능한데 테스트가 없다** — 별도 비용 없이 추가할 수 있는 항목.

## 후보 1 · User 모듈을 세션·시계·DB 큐에서 떼어낸다 — **Strong** ⭐ 최우선

**파일**: `User/User.cs` · `User/User.WorkStation.cs` · `User/User.Inventory.cs` · `User/User.Currency.cs` · `Common/GatheringScheduler.cs`

**문제** — 순수 코어가 받는 `now` 주입이 `User`에서 끊긴다.

- `AssignWorkStation`(`User.WorkStation.cs:71`) · `RefreshWorkStationSpeed`(`:110`)는 `now`를 인자로 못 받고 내부에서 `DateTime.UtcNow`를 생성한다.
- 생성자가 `internal` + `ISession` 필수(`User.cs:31`)이고 `InternalsVisibleTo`가 없어 **테스트 프로젝트에서 `new User(...)`가 컴파일조차 안 된다.**
- `OnCreate`가 `DBManager.Instance`로 실제 DB에 붙는다(`User.cs:74`).
- `GatheringScheduler.Tick`은 `private static` + `Timer` + `UtcNow` + `UserManager.Instance.All`(`GatheringScheduler.cs:42-57`) — 서버 권위 정산 루프 전체에 진입점이 없다.

**해결** — seam 3개를 연다: **시계(`IClock`) · 패킷 송신 · DB 큐**를 생성자 주입으로 바꾸고,
`now`를 못 받던 두 메서드에 인자를 뚫는다. `GatheringScheduler`도 clock·유저 소스를 받으면 같은 seam에 얹힌다.

- `IClock` 스케치는 **테스트 프로젝트에 이미 있다** — `SmokeTest.cs:11-14`의 `IDummyClock`, 주석에 "채취 정산을 테스트할 때 이 형태를 그대로 쓴다"고 예고까지 돼 있다.

**얻는 것**
- 레버리지: seam 3개로 441줄이 한꺼번에 열린다 — `SettleWorkStation` / `AssignWorkStation` / `ResolveSlotSpeed` / `GainItem` 전부.
- 기획 규칙 "속도를 바꾸기 직전에 반드시 정산한다"(게임기획코어 6장)를 처음으로 테스트로 검증할 수 있게 된다.
- 후보 2·6의 선행 조건.

## 후보 2 · 로그인 플로우를 리포지토리에서 회수한다 — **Strong**

**파일**: `Repository/LoginRepository.cs` · `Repository/AccountRepository.cs` · `User/User.DB.cs`

**문제** — DB 계층이 로그인 게임 플로우를 지휘한다. `LoginRepository`(170줄)가 DB 스레드에서:

- 신규 캐릭터 지급 INSERT (`:66-77`) — 상수 `DefaultCharacterTid`는 `User.Character.cs:8`에 있는데 사용은 여기
- 기본 슬롯 개설 (`:102-114`) — 도메인 메서드 `WorkStation.Unlock`이 있는데 안 쓰고 직접 `new WorkStationSlot`
- "채취는 지금부터 시작" 시각 결정 (`:119`) — **DB 스레드가 `DateTime.UtcNow`로**
- `Apply()`가 `User.LoadDB` → `User.Login()`을 직접 호출 (`:133-134`) — 응답 전송까지 리포지토리가 트리거

`AccountRepository`는 밴/삭제 판정 분기가 빈 주석뿐이라 **밴 유저는 응답 없이 무한 대기한다**(`AccountRepository.cs:57-68`).

**해결** — 리포지토리는 `LoginData` 결과 객체를 반환하는 데서 멈춘다.
신규 지급·슬롯 개설·시작 시각·다음 단계 호출은 로직 스레드의 User 쪽 플로우가 맡는다.
정책이 순수 코드가 되므로 DB 없이 테스트된다.

**얻는 것** — 신규 유저 정책의 지역성(한 곳), 리포지토리 인터페이스가 "데이터 왕복"으로 좁아짐, 밴 응답 누락 같은 침묵 실패가 드러남.

## 후보 3 · 가챠를 WeightedPicker 위로 접는다 — **Strong**

**파일**: `Gacha/GachaTable.cs` · `Gacha/GachaService.cs` · `Common/WeightedPicker.cs` · `User/User.Inventory.cs`

**문제** — 같은 알고리즘이 2벌이다.

| | `WeightedPicker` | `GachaTable.PickOne` (`GachaTable.cs:50-64`) |
| --- | --- | --- |
| 알고리즘 | 누적합 + 이진 탐색 | 선형 스캔 (매 Draw마다 totalWeight 재계산) |
| 난수 | 주입 가능 (`Random?`) | `Random.Shared` 하드코딩 (`:53`) |
| 검증 | 가중치 0 제외·음수 거부·합 오버플로 검사 | 없음 |
| 테스트 | 200줄 | 0줄 |

"itemId별 합산 후 GainItem" 루프도 2벌이다 — `GachaService.cs:41-46`과 `User.WorkStation.cs:44-46`.

**해결** — `GachaEntry`는 이미 `Weight`를 가지므로 `WeightedPicker.From(pool, e => e.Weight)` 한 줄로 대체하고 `PickOne`을 삭제한다.
합산-지급은 `User.GainItems(IReadOnlyDictionary<int,int>)` 하나로 통합한다.

**삭제 테스트 통과**: `PickOne`을 지우면 복잡도가 `WeightedPicker` 한 곳으로 집중된다 — pass-through가 아니라 진짜 중복이었다는 증거.

**얻는 것** — 추첨 인터페이스 1개에 소비자 3곳(드롭·희귀도·가챠), 가챠가 기존 테스트 200줄을 공짜로 얻는다.

## 후보 4 · Executor를 MikaNetwork.Lib에서 꺼낸다 — **Worth exploring**

**파일**: `MikaNetwork.Lib/MikaNetwork.Server/MikaExecutor.cs` · `DB/DBManager.cs` · `Common/Entity.cs`

**문제** — "프레임워크는 게임을 모른다"(CLAUDE.md 경계 규칙)를 Lib 스스로 어긴다.

- `DBExecutor` + `LogicExecutor`가 **네트워크 라이브러리 안에** 있다(`MikaExecutor.cs`). 그 결과 게임 코드 3곳(`Entity.cs` · `DBManager.cs` · `GatheringScheduler.cs`)이 네트워크 lib을 using한다.
- `Entity.Post`가 `LogicExecutor.Instance`에 못 박혀(`Entity.cs:34`) 어떤 Entity 생명주기도 동기 검증이 안 된다.
- 실행기가 예외를 `Console.WriteLine` 후 삼킨다(`MikaExecutor.cs:47-55`) → `Apply` 미도달 → **로그인 무한 대기의 근원**.

**해결** — 두 Executor를 WSGameServer로 옮기고 `IJobScheduler` seam을 게임 쪽에 둔다.
Lib은 이미 `onRecvCallback` 파라미터를 받으므로 Lib 쪽 변경은 거의 없다.
옮기는 김에 실패 훅(`OnError`)을 뚫어 침묵 실패를 없앤다.
어댑터 2벌(실제 스레드 / 테스트 인라인 실행)이 seam을 정당화한다.

## 후보 5 · ServerLog·패킷 훅에 어댑터 seam을 연다 — **Worth exploring**

**파일**: `Common/ServerLog.cs` · `MikaNetwork.Core/MikaPacketManager.cs` · `MikaProtocol/MikaSessionPacketExtensions.cs`

**문제** — 두 번째 어댑터가 이미 문서화돼 있는데 인터페이스가 없다.

- `ServerLog`는 static + `Console` 직결 + 정적 생성자에서 `Console.OutputEncoding` 프로세스 전역 변경(`ServerLog.cs:57-67`). 주석 스스로 "Unity에서는 Console.WriteLine이 안 뜬다"고 적어 뒀다 — 어댑터 2개(서버 콘솔 / Unity Debug.Log)의 존재를 인정하면서 seam이 없다.
- 패킷 훅 3개(`Dispatching` · `UnknownReceived` · `Sent`)가 전부 **정적 mutable** — 프로세스당 1개만 배선된다. 서버/더미클라를 한 프로세스에 띄우는 통합 테스트가 불가능하다. `PacketLogger.cs:12-14` 주석이 스스로 이 한계를 적어 뒀다.

**해결** — `ILogSink` 인터페이스 + 콘솔 어댑터 기본. 패킷 훅은 `MikaPacketManager` 인스턴스 프로퍼티로 내린다
(이미 인스턴스 클래스라 비용 ≈ 0). 호출부 시그니처는 유지되므로 변경 반경이 작다.

## 후보 6 · "정산 → 속도 변경" 불변식을 타입으로 만든다 — **Speculative**

**파일**: `User/WorkStation/WorkStationSlot.cs` · `User/WorkStation/WorkStation.cs` · `User/User.WorkStation.cs`

**문제** — "속도를 바꾸기 직전에 반드시 정산한다"(소급 지급 방지)가 주석(`WorkStationSlot.cs:118-119, 136-139`)과
호출 순서(`User.WorkStation.cs:87-93, 110-114`)로만 지켜진다. `ApplyWorkSpeed`를 먼저 부르는 새 호출자가 생기면
컴파일은 통과하고 재화만 샌다.

**해결** — `ApplyWorkSpeed`를 공개 인터페이스에서 내리고 `WorkStation.SettleAndApplySpeed(now, resolver)` 원자 연산 하나로 접는다.
인터페이스에서 메서드가 하나 줄고, 불변식이 구현 안으로 들어간다.

현재 호출자가 2곳뿐이라 급하지 않다. 후보 1 이후에.
