# 게임 기획 참조 (게임 작업 전 필독)

> 최종 업데이트: 2026-08-02
>
> 게임 시스템·콘텐츠를 만지기 전에 **[`GameDesign/기획/게임기획코어.md`](../../../../GameDesign/기획/게임기획코어.md)** 를
> 먼저 읽고, 그 다음 해당 영역의 **상세 기획안**을 읽는다.
> 게임기획코어는 "무엇을 왜 만드는가", 상세 기획안은 "어떻게 만드는가"를 담는다.
>
> **기획 문서를 고쳤으면 [`문서관계도.md`](../../../../GameDesign/기획/문서관계도.md)의
> 역참조를 따라 재귀적으로 전파한다** (아래 "기획을 바꿨으면 어디까지 바꾸는가").

---

## 트리거 — 언제 읽는가

**게임의 규칙·수치·콘텐츠에 닿는 모든 작업.** 예:

- 채취/퀘스트/특성/아이템/거래/성장 관련 로직 구현·수정
- `GameDesign/Excel/*.xlsx` 데이터 추가·변경
- 게임 데이터 테이블(`GameData`) 스키마 변경
- 게임 관련 패킷·DB 테이블 설계
- 바탕화면 위젯·팝업 UI 등 게임 표현 작업
- 기획 문서 자체의 수정·추가

## 읽지 않아도 되는 경우

- 게임 규칙과 무관한 순수 인프라 작업 (빌드 스크립트, 로깅, 네트워크 계층 자체 등)
- 파일을 바꾸지 않는 단순 질의응답

---

## 절차

1. **[`GameDesign/기획/게임기획코어.md`](../../../../GameDesign/기획/게임기획코어.md) 를 읽는다.** (항상, 예외 없이)
   - 특히 **5장 "확정 / 미확정 현황"** 을 확인한다.
   - **6장 "개발 시 지켜야 할 접점"** 의 고정 규칙을 지킨다.
2. 게임기획코어의 **3장 시스템 지도**에서 이번 작업에 해당하는 시스템을 찾아,
   그 **상세 기획안**(`GameDesign/기획/<시스템>/README.md`)을 읽는다.
   - 여러 시스템에 걸치면 관련된 것을 전부 읽는다.
   - 각 문서 말미의 **"결정 필요 (Open Questions)"** 를 반드시 확인한다.
3. **[`문서관계도.md`](../../../../GameDesign/기획/문서관계도.md) 2.2에서 그 문서의 정참조를 본다.**
   함께 읽어야 할 문서가 거기 있다. 각 문서 헤더의 `상위`/`전제` 줄도 같은 정보를 준다.
4. 설계 판단이 갈리면 게임기획코어 1장의 **설계 원칙(P1~P4)** 을 기준으로 결정한다.
5. 리스크가 걸리는 작업이면 [`GameDesign/기획/기획평가.md`](../../../../GameDesign/기획/기획평가.md)
   의 리스크 등급표를 함께 본다.

## 지켜야 할 것

### 미확정 항목을 임의로 정하지 않는다

게임기획코어 5장과 각 상세 기획안의 "결정 필요"에 있는 항목은 **아직 기획이 없는 것**이다.
구현에 그 값이 필요하면 **사용자에게 먼저 확인한다.** 임의로 정해서 구현하지 않는다.

부득이하게 진행해야 하면, 가정을 명시하고 임시값임을 코드/문서에 남긴다.

### 기획과 다른 구현을 발견하면 알린다

코드가 기획 문서와 다르면 조용히 한쪽에 맞추지 말고, **차이를 사용자에게 보고**한다.
문서가 낡은 것인지 구현이 틀린 것인지는 사용자가 판단한다.

### 밸런스 수치는 코드에 넣지 않는다

수치·테이블은 `GameDesign/Excel/*.xlsx`가 원본이다.
엑셀 수정 후 `GameDesign/generate-tables.ps1`을 돌려 생성물까지 같은 커밋에 담는다.
생성물(`Server/GameData`, `Server/Shared/Data`, `GameDesign/DataLog`, Unity 미러)은 직접 수정하지 않는다.

### 기획을 바꿨으면 어디까지 바꾸는가 — 재귀 전파

**한 문서만 고치고 끝내지 않는다.** 이 저장소에서 실제로 반복된 사고는
"하위 문서만 고치고 상위·형제를 안 고친 것"이다
(`Hunting` enum · 아이템 30종 → 150종 · `ItemRarity` → `GlobalRarity` — 2026-08-02 확인).

문서를 고쳤으면 **그 문서 헤더의 `바뀌면 갱신` 블록**(또는
[`문서관계도.md`](../../../../GameDesign/기획/문서관계도.md) 2.1)에 적힌 문서를
**전부 열어 본다.** 고친 문서가 생기면 **그 문서에서 또 퍼진다.**

```
큐 = [고친 문서]
방문 = {}
while 큐:
    문서 = 큐.pop()
    if 문서 in 방문: continue      ← 순환(캐릭터 ↔ 작업슬롯)은 여기서 멈춘다
    방문.add(문서)
    for 대상 in 그 문서의 "바뀌면 갱신" 목록:
        대상을 연다
        if 이번 변경으로 대상의 서술이 낡았나?
            대상을 고치고, 대상의 "최종 업데이트"를 오늘로 바꾸고, 큐에 넣는다
        else:
            넘어간다                ← 열어 보고 안 고치는 것이 정상이다
```

| 규칙 | 내용 |
| --- | --- |
| **깊이 제한 없음** | 2·3단계까지 간다. 보통 2단계에서 자연히 멎는다 |
| **고친 문서만 큐에 넣는다** | 열어 보고 그대로면 거기서 가지가 끝난다 |
| **날짜는 고친 문서만** | 안 고친 문서의 날짜를 올리면 역전 검사가 무력해진다 |
| **`게임기획코어` 5장은 항상** | 확정/미확정이 바뀌었으면 반드시 반영한다 |
| **`⚠️`(제안) 표기 제거** | 확정됐으면 해당 표기를 지운다 |

**무엇이 "낡게 만드는" 변경인가** — 아래에 해당할 때만 대상을 손댄다.
표현만 다듬은 것은 전파하지 않는다.

| 유형 | 예 |
| --- | --- |
| 이름이 바뀜 | `ItemRarity` → `GlobalRarity` |
| 수치·개수가 바뀜 | 아이템 30종 → 150종 |
| 확정 상태가 바뀜 | ❌ 미정 → ✅ 확정 |
| 폐지 | 요일 로테이션 폐지 |
| 구조가 바뀜 | 판정 비용이 상수 → 테이블 |

### 전파는 문서에서 끝나지 않는다 — 엑셀·코드까지

확정된 기획은 **엑셀 → 생성물 → 서버 코드** 순으로 흐른다.
대응표는 [`문서관계도.md`](../../../../GameDesign/기획/문서관계도.md) 4장에 있다.

> ⚠️ **엑셀만 앞서 나가면 "미구현"이 아니라 "오동작"이 된다.**
> 2026-08-01에 드롭 시트가 레벨별로 갈라졌는데 `DropTableCatalog`가 `IndustryLevel`을
> 읽지 않아 **Lv1 슬롯에서 Lv5 아이템이 나오는 상태**가 됐다.
> 엑셀 구조를 바꿀 때는 **그 시트를 읽는 서버 코드를 같은 작업 단위로** 본다.

코드가 못 따라가면 [`일감/`](../../../../일감/README.md)에 등록하고,
문서에 `❌ 미구현 (일감 T-0XX)`를 **반드시** 적는다 — 안 적으면 다음 사람이 "구현됐다"고 읽는다.

### 고쳤으면 검사한다

```powershell
powershell -File GameDesign/check-doc-graph.ps1 -Changed   # 이번에 고친 문서 기준 (커밋 전)
powershell -File GameDesign/check-doc-graph.ps1            # 전수 점검
powershell -File GameDesign/check-doc-graph.ps1 -Fix       # 헤더 블록을 실제 그래프에 맞춤
```

| 결과 | 뜻 |
| --- | --- |
| **오류** (깨진 링크 · 블록 불일치) | 반드시 고친다. 링크를 추가·삭제했으면 `-Fix` |
| **경고** (갱신일 역전) | **전파를 빠뜨렸을 수 있다.** 확인하고, 정말 영향이 없었다면 그대로 둔다 |

> 링크를 새로 걸거나 지웠으면 `-Fix`로 헤더 블록을 맞추고
> `문서관계도.md` 2장 표도 `-Graph` 출력으로 갱신한다.

## 새 시스템·산업을 추가할 때

1. `GameDesign/기획/<시스템>/README.md` 를 만든다.
   **폴더명·문서명은 반드시 한글로 짓는다.** (`Gathering` ❌ / `자원채취` ⭕)
   1차 산업이면 `GameDesign/기획/자원채취/<산업>/README.md`.
2. 기존 문서와 같은 구성을 따른다:
   `확정 사항` → `설계(제안)` → `데이터 설계` → `서버/클라 책임` → `결정 필요`
   헤더에는 `> 상위 문서:` · `> 최종 업데이트:` 두 줄을 반드시 둔다
   (검사 스크립트가 이 형식을 읽는다).
3. `게임기획코어.md` **3장 시스템 지도**(산업이면 **4장 콘텐츠 지도**)에 행을 추가한다.
4. **[`문서관계도.md`](../../../../GameDesign/기획/문서관계도.md) 1·2장에 행을 추가**하고,
   `check-doc-graph.ps1 -Fix`로 헤더의 `바뀌면 갱신` 블록을 생성한다.
5. 이 스킬의 **문서 지도** 표에도 행을 추가한다.

> 이름 규칙의 전체 내용(예외 목록 포함)은 [`CLAUDE.md`](../../../../CLAUDE.md)의 **"이름 규칙 (문서·폴더)"** 참조.
> `GameDesign/Excel`·`GameDesign/DataLog`는 코드가 경로를 직접 참조하므로 **영문을 유지한다.**
