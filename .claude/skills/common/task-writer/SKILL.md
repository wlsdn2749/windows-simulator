# 일감 작성·갱신

> 해야 할 일을 `일감/`(저장소 루트)에 **일감 1개 = 파일 1개**로 남긴다.
> 짝이 되는 스킬은 [`task-reader`](../task-reader/SKILL.md)(작업 전 일감 확인)다.

---

## 트리거 — 언제 쓰는가

| 상황 | 할 일 |
| --- | --- |
| 새 할 일이 생겼다 | 새 일감 파일 + INDEX 한 줄 추가 |
| 일감을 시작했다 | `상태: 진행중`으로 변경 |
| 일감을 끝냈다 | `상태: 완료` + **관련 커밋 해시 기록** |
| 막혔다 | `상태: 보류` + 무엇에 막혔는지 명시 |
| 담당·마감·범위가 바뀌었다 | 해당 필드 수정 |

### 일감으로 만들지 않는 것

- **지금 바로 처리하는 일** — 한 번의 대화 안에서 끝나면 일감이 아니다.
- 작업 로그 — 그건 [`agent-log-writer`](../agent-log-writer/SKILL.md)의 몫이다.
  일감은 **앞으로 할 일**, Agent 로그는 **이미 한 일**이다.
- 기획 문서에 이미 "❌ 미확정"으로 적힌 항목을 **그대로 옮겨 적는 것**.
  일감으로 올릴 때는 "무엇을 결정해야 하고 그게 무엇을 막고 있는지"를 함께 적는다.

---

## 파일 규칙

- 위치: `일감/` (저장소 루트)
- 파일명: `T-<3자리>-<한글슬러그>.md` — 예: `T-001-하트비트.md`
- **ID는 재사용하지 않는다.** 일감이 취소돼도 번호를 비워 두고 다음 번호를 쓴다.
  커밋 메시지·대화에서 "T-003"으로 참조되므로 번호가 재사용되면 과거 기록이 다른 일을 가리키게 된다.
- 완료된 일감도 **삭제하지 않는다.** `상태: 완료`로 남겨 둔다 — 왜 그렇게 했는지의 기록이다.

---

## 일감 템플릿

```markdown
---
id: T-001
제목: <한 줄 제목>
담당: 서버          # 클라 / 서버 / 공용
상태: 대기          # 대기 / 진행중 / 완료 / 보류
우선순위: 높음      # 높음 / 보통 / 낮음
마감: 미정          # YYYY-MM-DD 또는 미정
---

# T-001 <제목>

## 배경

왜 이 일이 필요한가. 안 하면 무엇이 문제인가.

## 할 일

- [ ] 항목 1
- [ ] 항목 2

## 완료 조건

이 일감을 "끝났다"고 부를 수 있는 상태. 애매하면 영원히 안 끝난다.

## 막고 있는 것 / 선행 일감

- 없으면 "없음"
- 다른 일감이 먼저면 `T-002` 형태로 적는다

## 관련 커밋

- 없으면 "없음". 작업하면서 커밋할 때마다 `해시 — 한 줄 요약` 형태로 추가한다
```

---

## 필드 값

| 필드 | 허용값 | 비고 |
| --- | --- | --- |
| `담당` | `클라` · `서버` · `공용` | 기획 결정처럼 양쪽이 함께 볼 일은 `공용` |
| `상태` | `대기` · `진행중` · `완료` · `보류` | `보류`는 **막힌 것**, `대기`는 아직 시작 안 한 것 |
| `우선순위` | `높음` · `보통` · `낮음` | |
| `마감` | `YYYY-MM-DD` 또는 `미정` | **모르면 임의로 날짜를 넣지 않는다.** 안 지킬 날짜는 없느니만 못하다 |

> `보류`와 `대기`를 구분하는 이유: 보류는 **사람이 무언가를 결정해 줘야** 풀리고,
> 대기는 그냥 순서가 안 온 것이다. 섞이면 "왜 이게 안 굴러가지"를 매번 다시 파악해야 한다.

## 큰 작업 쪼개기 — 일감 여러 개로 나눌 때

기획·대화에서 나온 큰 덩어리를 일감으로 옮길 때는 아래 규칙으로 나눈다.
(한 일감으로 충분한 크기면 이 절은 건너뛴다.)

### 수직으로 자른다

각 일감은 **좁아도 끝까지 관통하는 조각**(tracer bullet)이어야 한다.
"엑셀만" · "패킷만" · "DB만" 같은 **층 단위 분할은 금지** — 층 하나짜리 일감은
끝나도 단독으로 확인할 방법이 없고, 마지막 일감에서야 통합 문제가 터진다.

| | 예 |
| --- | --- |
| ❌ 수평 | `T-A 엑셀 시트` → `T-B DB 컬럼` → `T-C 패킷` → `T-D 서버 로직` |
| ✅ 수직 | `T-A 레벨 1개가 엑셀→서버→패킷까지 실제로 돈다` → `T-B 해금 검증 추가` |

- **완료한 일감은 그 자체로 확인 가능**해야 한다 (더미 클라·테스트·로그로 눈에 보임).
- 크기는 **한 번의 작업 세션에 끝날 만큼.** 그보다 크면 더 쪼갠다.
- 사전 정리(prefactoring)가 필요하면 **그것부터 별도 일감**으로 앞에 둔다.

### 선행 일감은 "진짜 게이트"만 적는다

`선행 일감`은 **그것 없이는 시작조차 못 하는 것**만 적는다.
"먼저 하면 좋은 것"은 선행이 아니라 `일감/README.md`의 **순서 메모**에 적는다.

- 선행이 모두 끝난 일감이 **착수 가능선**이다. 어디부터 할지 고민할 필요가 없어진다.
- 결정 대기는 선행 일감이 아니라 **`상태: 보류` + 막힌 결정 명시**로 표현한다 (기존 규칙).

### 예외 — 전면 개명·이설은 확장–수축으로 자른다

컬럼 개명, TID 대역 이설처럼 **한 번에 바꾸면 전체가 깨지는 기계적 변경**은
수직으로 자를 수 없다. 이때만 순서를 셋으로 나눈다:

1. **확장** — 새 형태를 옛것 옆에 추가 (아무것도 안 깨짐)
2. **이행** — 참조처를 묶음 단위로 옮김 (묶음마다 일감, 전부 1에 막힘)
3. **수축** — 참조가 0이 된 뒤 옛것 삭제 (모든 이행에 막힘)

> 낚시 TID 이설(`1001~` → `10001~`)이 실제 사례다 — 구 TID 정리(수축)가
> T-005에 남아 있는 이유가 이 순서 때문이다.

### 등록 전에 분해안을 검토받는다

일감을 파일로 만들기 **전에** 목록(제목 · 선행 · 완료 시 보이는 것)을 보여 주고 묻는다:
굵기가 맞는가 / 선행 관계가 진짜인가 / 합치거나 더 쪼갤 것이 있는가.
승인 후 등록한다 — 일감 번호는 재사용하지 않으므로 **등록 후 재편은 비싸다.**

---

## 마무리 절차 (필수)

1. `일감/T-<번호>-<슬러그>.md`를 위 템플릿으로 작성/수정한다.
2. `일감/README.md`의 표에 한 줄을 추가하거나, 바뀐 칸을 고친다.
   - 파일의 프론트매터와 INDEX 표가 **어긋나면 안 된다.** 한쪽만 고치지 않는다.
3. 답변 말미에 어떤 일감을 만들었는지/바꿨는지 한 줄로 알린다.

## 커밋과의 관계

일감을 끝낸 커밋을 만들었으면 **그 해시를 일감의 `관련 커밋`에 적는다.**
반대로 커밋 메시지에 일감 ID를 넣을지는 자유다 — 한쪽만 연결돼 있어도 추적은 된다.
