# 산업 레벨 시스템 기획

## 목적 / 배경

- 사용자 요청: **"각 산업별 레벨 시스템을 만들거야. 경험치는 없고 특정 조건이 되면 다음 레벨이 해금되는 시스템"**
- 확인 결과 기존 기획에 **산업 레벨이라는 개념은 없었다.** 산업을 가르는 축은
  회당 산출·희귀도 분포(수치 2개)와 산업별 고유 메커니즘뿐이었다.
- 사용자가 정한 것 (선택지 제시 후):
  - **레벨은 합산되지 않는다.** 슬롯에 배치할 때 **어떤 산업, 어떤 레벨**로 할지 고른다
  - **레벨의 효과 = 드롭 테이블 확장**
  - **해금 조건은 미정** — 임의로 정하지 않았다

## 주요 결정 / 근거

**1. 해금은 계정, 선택은 슬롯**

사용자가 "합산되지 않는다"고 했으므로 레벨 자체는 슬롯이 고르는 값이다.
다만 **해금 상태까지 슬롯에 두면 슬롯을 늘릴 때마다 같은 조건을 다시 채워야 해서
슬롯 확장이 곧 후퇴가 된다.** 그래서 해금만 계정에 둔다.

**2. 이 시스템이 낚시터·사냥터·수종을 통합한다**

5개 산업이 각자 다른 이름(`SpotTID`·`FieldTID`·`TreeTID`)으로 같은 것 —
"슬롯이 어떤 드롭 세트를 쓸지" — 을 갖고 있었다. `IndustryLevel` 하나로 모았다.
**부수 효과로 낚시의 "고유 메커니즘이 없는 유일한 산업" 문제가 해소된다.**

폐지된 테이블: `FishingSpotTable` · `HuntingFieldTable` · `TreeTable`

**3. 농사·채굴만 정합하지 않아 결정으로 남겼다**

- 농사: 파종(A안 = 드랍 세트 선택)이 레벨과 **같은 일**을 한다. 흡수 vs 2층
- 채굴: 깊이는 **누적**(자동), 레벨은 **선택**(해금). 성격이 다르다.
  **갱도(레벨) × 깊이(누적) 2층**을 권장했다 — 스노우볼 정체성을 지키기 위함

**4. 속도·산출량이 아니라 드롭 목록만 건드린다**

사용자가 "드롭 테이블 확장"을 골랐고, 이게 구조적으로도 옳다.
총량 = 접속 시간 × 슬롯 수 × 속도 배수인데 여기에 레벨이 곱해지면 항이 넷이 된다.
레벨은 **나오는 종류**만 바꾸고 개수·속도는 그대로 둔다.

**5. 상위 레벨을 "더 좋게" 만들지 않는 쪽으로 설계했다**

`하위 레벨도 계속 고를 수 있다`가 확정인데, 상위가 상위호환이면 그 확정이 죽는다.
**상위 레벨에서는 하위 아이템이 나오지 않게** 하고 하위 재료에 수요를 두는 안(A)을 기본으로 잡았다.
속도로 균형을 잡는 안(B)은 `JudgeCost`가 전역 상수라 **비권장**으로 명시했다.

## 후속 작업 / 주의사항

- **코드·엑셀은 아무것도 건드리지 않았다.** 해금 조건이 미정이라
  `IndustryLevelTable`의 컬럼 구성을 확정할 수 없다 (T-016 → T-017)
- ⚠️ **하위 아이템의 수요처가 기획에 없다.** 특성 재료는 미작성이고 제작 시스템은 없다.
  이게 채워지지 않으면 A안은 이름만 남고 실제로는 전부 최고 레벨로 수렴한다
- ⚠️ `<산업>BasicTable` 5종에 `IndustryLevel` 컬럼이 붙고 행이 레벨 배수로 늘어난다.
  **T-005(드롭 테이블)와 같은 시트라 순서가 겹치면 충돌한다**
- ⚠️ 벌목: 숲 자원량을 레벨별로 두면 **고갈될 때마다 레벨을 갈아타는 회피**가 가능하다.
  하나로 두면 레벨 변경이 고갈을 이어받는다. 어느 쪽이든 정해야 한다
- `IndustryLevel`의 `Ref` 검사 방식이 열려 있다 —
  `IndustryLevelTable.Level`은 키가 아니라 참조 대상이 될 수 없다
- 두 UI 목업(`게임UI목업.html`·`작업슬롯UI목업.html`)이 레벨 없는 배치로 그려져 있다.
  T-016 후 갱신 필요
